# Отчёт о производительности трассировки TPC MPD

Дата измерений: 2026-09-23. Анализ выполнен без изменения физических алгоритмов,
геометрии, числа лучей, оптических свойств, порогов отсечения и настроек
визуализации. Добавлены только отдельные benchmark-файлы.

## Краткий вывод

Главное узкое место интерактивного режима — полный перебор всех 184 поверхностей
для каждого активного луча на каждом поколении. За один расчёт выполняется
122 931 136 проверок «луч–поверхность»; поиск ближайшего пересечения занимает
12,39 с из 13,68 с трассировки. Полный интерактивный subprocess занимает 18,07 с.

Второе независимое узкое место полного (не интерактивного) запуска — CSV:
9,30 с и резкий рост peak working set до 682 MiB из-за преобразования 745 503 строк
в список Python-словарей. CSV в интерактивном режиме уже отключён.

Наиболее перспективная точная оптимизация — broad phase/BVH или иное точное
пространственное отсечение поверхностей с последующей проверкой существующими
формулами. Быстрые и малорисковые улучшения: генерировать исходный пучок один раз,
не перечитывать/перезаписывать готовый HTML ради панели управления и сохранять
неизменяемые данные в долгоживущем интерактивном worker.

## Архитектура вычислений

1. При импорте читаются восстановленные координаты микросборок и изменяются
   глобальные конфигурации зеркал.
2. `build_initial_source()` копирует шаблон источника; `emit_initial_rays()`
   увеличивает число радиальных колец до получения не менее 20 000 лучей.
3. `build_initial_scene()` создаёт оптические элементы и 16×7 микрозеркал.
4. `RayTracer.__post_init__()` компилирует Scene в 184 backend-поверхности.
5. `RayTracer.trace()` выполняет поколения лучей. Для каждого поколения
   `CompiledScene.find_nearest()` последовательно вызывает `intersect()` каждой
   поверхности на всём массиве активных лучей.
6. По ближайшим поверхностям лучи группируются, отражаются/преломляются,
   разделяются и снова объединяются в один `RayBundle`.
7. Сегменты и попадания переводятся в host-массивы, затем создаются summaries,
   CSV и Plotly HTML.
8. Интерактивный POST запускает новый Python subprocess, который повторяет весь
   путь с `--skip-csv`, записывает HTML и завершается.

Ожидаемый эффект ниже — гипотеза, пока не измеренное ускорение.

## План оптимизации

1. Зафиксировать regression/golden suite до изменений: ray lineage и counts,
   surface sequence, координаты/направления, detector hits, мощности и энергии.
2. Исправить генерацию источника на один `emit()` и интеграцию HTML controls в
   одну запись. Это малый риск и ожидаемо убирает около 2,2–2,6 с interactive.
3. Убрать лишнюю нормализацию/copy в trusted операциях `RayBundle`, измеряя после
   каждого изменения отдельно.
4. Сделать microbenchmark вариантов `dot` и plane intersection на реальных
   формах 20k–80k; выбрать только измеренно лучший вариант.
5. Реализовать точный broad phase сначала для 16 bundle assemblies, затем для
   всей статической сцены. Existing intersection остаётся narrow phase.
6. После broad phase рассмотреть chunked batched plane kernel. Не создавать
   массивы размера `rays × all surfaces` без лимита памяти.
7. Перевести интерактивный сервер на persistent worker с immutable source cache
   и canonical mirror state. Новый request не должен наследовать поворот прошлого.
8. Только после CPU-оптимизаций повторить GPU-анализ на машине с CUDA/CuPy:
   таймеры обязаны синхронизировать stream; отдельно считать transfer и kernels.
9. Оптимизировать CSV streaming и Plotly selection как независимые postprocess
   задачи; они не должны блокировать улучшение физического ядра.

## Возможность частичного интерактивного retrace

Теоретически можно кешировать лучи до первого регулируемого зеркала и пересчитывать
только downstream-ветви. Потенциал высокий для поздних зеркал, но это более
рискованный второй этап: поворот плоскости меняет точку её пересечения, а разные
ветви могут повторно встретить регулируемые элементы. До реализации нужен exact
dependency/event replay и доказательство, что кешированная upstream-часть не зависит
от изменённой геометрии. Начинать следует с persistent worker + BVH: эти улучшения
проще проверить и не требуют изменения физической семантики.
