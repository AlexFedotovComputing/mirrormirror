# Статическая реконструкция по измерениям

`mirrorlab.calibration.analyze_measurements(direction, fit_lavsan=False)` читает
исходные файлы без изменения. `west_to_east` соответствует `из-к+`,
`east_to_west` — `из+к-`. В отчёте единицы — метры; невязки и исходные
коэффициенты таблицы явно обозначены миллиметрами. Каждая строка содержит
стержень, окно, номер луча и адрес ячеек источника.

## Что содержится в Optimis_code

Предоставленный `Optimis_code-main.zip` сохранён распакованным в
`legacy/optimis_code`. README архива содержит название `-`. Исходники и отчёты
описывают оптимизацию быстродействия: предварительный отбор кандидатов
пересечения (`raytrace.py`, `OPTIMIZATION_REPORT.md`) и однократную генерацию
гауссова пучка (`SOURCE_OPTIMIZATION_REPORT.md`). В архиве нет алгоритма
подгонки геодезических измерений или регистрации лавсановых точек. Поэтому
описанный ниже подбор лавсана — самостоятельная воспроизводимая реализация,
а не утверждение о восстановлении неизвестного исходного алгоритма.

## Проверка сохранённых уравнений

Для двух полных точек экранов строится `p(s) = P1 + s (P2 − P1)`.
В API направление нормировано, а `coefficients_mm` сохраняет исходную
ненормированную параметризацию. При одной полной точке направление не
выдумывается; при отсутствии обеих точек луч остаётся отсутствующим.

На приложенных данных `из-к+`: 85 полных, 17 одиночных и 10 отсутствующих
измерений из 112. **111 из 112 строк** `из-к+_уравнения_лучей.txt` совпадают
с прямым вычислением, с допуском половины последнего десятичного знака
0,005001 мм. Единственное расхождение — стержень 4, окно 1, луч 3:
в Excel отсутствуют X/Y второй точки, а сохранённый TXT содержит полный
вектор `(397,52; 253,13; 14,76)` мм. Он не восстанавливается из имеющейся
строки Excel и не подставляется молча. Это сравнение показывает, что данный
TXT в основном содержит прямые через два экрана, а не результат лавсановой
оптимизации.

На данных `из+к-`: 83 полных, 18 одиночных и 11 отсутствующих измерений.
Ячейки `Лист1!F24` и `Лист1!F80` имеют формат даты, но исходные XML-числа
равны примерно 2,12 и 7,19 мм. Импорт читает их как числа и отмечает
несоответствие формата в предупреждениях. Неполные XYZ не трактуются как нули.

## Координаты сцены

Статическая сцена и отчёт используют исходные XYZ таблиц, в метрах:
`из-к+` содержит отрицательные z (ввод EAST), `из+к-` — положительные (ввод
WEST). Пометки интерфейса согласованы с этим: WEST +, EAST −. Имена файлов
сохранены; их знаки не используются для изменения чисел в измерениях.

Прежнее совмещение локальных нулей размещало оба кольца у центральной плоскости.
Координат колец в геодезии нет. По указанию пользователя они оценены через лучи
в `mirrorlab/coordinates.py`, с сохранением формы и размеров всей конструкции:

1. По двум полным экранным точкам строятся прямые. Для каждой микросборки
   оценивается общая точка их пересечения минимизацией расстояний до прямых
   с `soft_l1`, масштаб 2 мм. Она приближает центр семи отдельных микрозеркал;
   остаточная невязка этого приближения сохраняется в отчёте.
2. Центр цилиндрического газового объёма задаёт z=0. Проверяются оба направления
   оси z и два порядка окон. На имеющихся данных геодезические окна 1/2/3/4
   соответствуют локальным слоям 4/3/2/1. Это явное соответствие групп, а не
   переименование исходных измерений или доказанная перестановка отдельных лучей.
3. Для XY подбираются ориентации двух локальных систем и общий перенос оси
   объёма, с `soft_l1`, масштаб 5 мм. Допускается смена ориентации координатных
   осей; масштаб всегда единичный. Центры с большой внутренней невязкой
   пересечения лучей получают меньший вес. Ось цилиндра считается параллельной
   геодезической z; это явно записанное допущение, а не измеренный наклон.
4. Одна матрица на сторону применяется ко всей изображаемой оптике, источнику,
   сегментам и попаданиям. Идеальная и реальная геометрии используют одну привязку.
   Измеренные XYZ не преобразуются; их можно включить поверх сцены через легенду.

Результат `p_survey = Q p_local + t`, с ортогональной Q:

| Ввод | Q (строки) | t, м | RMS / максимум, мм |
| --- | --- | --- | --- |
| EAST | `(0.525151, 0.851009, 0); (0.851009, −0.525151, 0); (0, 0, −1)` | `(−0.000010, −0.000065, 1.7655)` | 29.769 / 71.896 |
| WEST | `(0.697439, 0.716644, 0); (−0.716644, 0.697439, 0); (0, 0, −1)` | `(−0.000010, −0.000065, −1.7655)` | 9.630 / 16.828 |

Центры колец оцениваются при z=±1.7905 м; границы цилиндра обеих моделей
совпадают при z=±1.665 м. Невязки в таблице — расстояния между зарегистрированными
центрами идеальных микросборок и их оценками из измерений. Это **оценочная
привязка**, а не метрологически подтверждённые координаты колец или результат
юстировки всех зеркал. Их индивидуальные нормали и положения не подгоняются.
Большая невязка EAST остаётся видимой, а не устраняется деформацией конструкции.

В JSON это `metadata.frame_registration` каждой стороны и
`static_frame_registration` отчёта измерений. Сохраняются матрица, перенос,
соответствие окон, опорные точки, невязки, допущения и источники. Пересчёт
кешируется с учётом изменения XLSX и идеальных снимков. Расчётное ядро остаётся
в локальной СК (`calculation_frame=legacy`); экспортируемая сцена — `survey`.

## Диагностика архивного преобразования таблиц

Следующее преобразование сохранено для воспроизведения старых результатов;
оно не используется для общего отображения двух сторон.

Для `west_to_east` привязка восстанавливается методом Кэбша по 102 полным
парам положений из `из-к+_уравнения_лучей.txt` и
`уравнения_лучей_в_СК_идеальной_геометрии.txt`. Для новой сцены дополнительно
применяется перенос старых координат z на −6,63974 м:

```text
R ≈ [[ 0.965314685, -0.261089180, 0],
     [ 0.261089180,  0.965314685, 0],
     [ 0,            0,           1]]
t ≈ (0.001590, 0.008790, 3.447220) м
p_scene = R p_survey + t
d_scene = R d_survey
```

Средняя квадратическая невязка опорных пар — 0,000410 мм, максимальная —
0,000708 мм; это согласуется с округлением уже преобразованной таблицы.
Так воспроизводится **сохранённое преобразование**, но не доказывается его
метрологическая точность. Если при обновлении данных максимум превысит
0,01 мм, преобразование таблиц не принимается автоматически.

Однако это **ещё не подтверждённая привязка к текущим зеркалам**. В
`legacy/_analyze_hex_bundle_fit.py` дополнительно явно задан разворот XY
для стержней 1 и 3 на 180°, отсутствующий в основной старой процедуре
ориентации зеркал. Он применяется только к `candidate_rays`. Без разворота
расстояния между линиями и центрами зеркал доходят до 1,943 м; с ним максимум
составляет 66,409 мм, что всё равно превышает предел перемещения зеркал
2 мм. Старые групповые и индивидуальные сдвиги также влияют на соответствие.

Поэтому `scene_registration.transform.accepted=true` означает лишь
воспроизведение пары таблиц; общий `scene_registration.accepted=false`
запрещает автоматическое применение к зеркалам. `candidate_rays` содержит
85 кандидатов и отдельные расстояния до текущих центров;
`scene_registration.rays` остаётся пустым до согласованной привязки.
Знак направления кандидатов выбирается от зеркала к экранным точкам.

Для `east_to_west` сопоставимой архивной пары файлов систем координат нет.
Новая привязка сцены выше использует непосредственно геодезические лучи,
а не эту пару таблиц. Подбор лавсана остаётся отдельной процедурой.

## Подбор лавсана

Поддерживается только файл `лавсан_из+к-.txt`, следовательно только
`east_to_west`. Принято явное соответствие индексов:
`стержень / окно / точка = стержень / микросборка / луч`. Перестановки
лучей не оптимизируются. Для каждого стержня используется отдельный
жёсткий поворот и перенос, без изменения масштаба или отражения:

```text
min Σ ||(I − dᵢ dᵢᵀ) (R pᵢ + t − oᵢ)||²,  R ∈ SO(3).
```

Перенос решается линейно для каждого пробного поворота. Поворот ищется
`scipy.optimize.least_squares` с 24 детерминированными начальными
приближениями: 12 азимутов для каждого из двух знаков локальной оси z.
Полные геодезические прямые фиксированы; масштаб остаётся единичным.
Параллельные прямые и коллинеарные опорные точки отвергаются как
недостаточные для однозначной привязки. После принятого преобразования
луч по двум экранным точкам и точке лавсана уточняется ортогональным МНК
(SVD); при одной экранной точке и лавсане получается восстановленный луч.

Результаты на текущих файлах:

| Стержень | Соответствий | RMS, мм | Принят для уточнения |
| --- | ---: | ---: | --- |
| 1 | 20 | 2,756 | Да |
| 2 | 20 | 2,198 | Да |
| 3 | 22 | 136,896 | Нет |
| 4 | 21 | 2,111 | Да |

У стержня 3 окна 3 и 4 имеют практически одинаковые координаты z около
1837 мм, тогда как геодезические уровни различны. Исходные точки сохранены,
результат минимизации и большая невязка показаны, но такой стержень не
используется для уточнения лучей. Это не исправляется догадкой на 330 мм.

Невязки являются ошибками подгонки на тех же данных, а не независимой
оценкой точности. Источники погрешностей, веса измерений, точность
соответствий индексов и однозначность минимумов требуют отдельной
метрологической проверки. Многозапусковый поиск не доказывает глобальный
минимум. Здесь не реализована волновая оптика или динамическая юстировка.

## Проверка

```powershell
python -m unittest discover -s tests -p test_calibration.py -v
```

Тесты проверяют восстановление известного пространственного преобразования,
вырожденные данные, ориентацию прямой, пропуски, исходные числовые ячейки,
сопоставление с TXT, привязку к сцене и отказ от применения несогласованного
лавсана третьего стержня.
